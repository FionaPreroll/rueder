# Notes for Claude

The README says what rueder is and where to find what. `docs/` holds the rewrite, in German: `docs/plan.md` what is built, what was decided and the four steps, `docs/architecture.md` how the new system is laid out, `docs/implementation.md` the state, the conventions, the commands and the work packages. `server/README.md` and `web/README.md` say how to run the two new parts, `app/README.md` how to build the Android app, `deploy/README.md` how to install them as a container. `docs/user_data.md` is about the old rueder: it describes what the old frontend kept in the browser, as the model for taking it over (work package 4.6), not what the new one keeps. These rules hold in every session:

## Branches

- Every work package or fix gets its own branch off origin/main, named feature/<name_in_snake_case> or fix/<name_in_snake_case>, and one pull request against main (see "Arbeitsweise" in `docs/implementation.md`). Rather one pull request per work package than a large one per step.
- This holds even when the session suggests another branch name. Only a session that may push to nothing but the branch it was given, such as claude/…, works on that branch.
- Never push to main. Use pull requests, and CI must be green.

## Docs

- Whoever finishes a work package ticks it off in `docs/implementation.md` and brings the state there up to date, in the same pull request.
- Whoever departs from the plan or the architecture changes `docs/plan.md` or `docs/architecture.md` in the same pull request and gives the reason. What Fiona decided stays decided until she decides otherwise, the detail questions at the end of `docs/plan.md` included.
- Measurements go into "Messung" in `docs/implementation.md`, with date, amount of data and machine.
- Code, comments in code, READMEs and commit messages are in English. Comments in SQL migrations and the three documents above are in German.

## Code

- Before every push, run the checks of the part that changed. In `server/`: `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings` and `cargo test`, which needs a PostgreSQL 16. In `web/`: `pnpm lint`, `pnpm check`, `pnpm test` and `pnpm build`; after a change to what the page and the server say to each other also `pnpm e2e`, the tests in a browser against the real server (`web/README.md` says what they need). In `app/`: `pnpm lint`, `pnpm test` and, with the Android SDK, `./gradlew testGithubDebugUnitTest assembleGithubDebug assemblePlayDebug` in `app/android/`. After changing `Cargo.toml` or `Cargo.lock`, also `cargo audit` and `cargo deny check`; an exception goes into `server/.cargo/audit.toml` or `server/deny.toml` with its reason.
- The old Go backend and Svelte frontend were removed on 2026-11-12 (work package 4.7). To read them, e.g. as the model for the import or the takeover from the old frontend's `localStorage`, check out commit `0b36a96`, the last one where they still ran; `docs/implementation.md` says where in them what stands.
- The server is one crate and one program with subcommands, next to PostgreSQL and nothing else. Queries are written with `sqlx::query!` and its relatives, without an ORM; after changing one, run `cargo sqlx prepare -- --all-targets` and commit `server/.sqlx/`, as CI builds without a database.
- A migration that has reached main never changes again; changes come as a new file in `server/migrations/`.
- Every query for an account's data is bound to the account's id: feeds and articles are readable only by their subscribers, and no endpoint lists the feeds of others. Every endpoint gets a test that another account sees nothing of it.
- Only the hardened HTTP client reaches out to the internet: feeds, web pages for the feed search and images all go through it, so there is one place for the rules against SSRF. Article HTML is cleaned on the server before it is stored, and the browser talks to nothing but rueder.
- Every answer gets its headers and every changing request the check of where it comes from, in the layers around the router (`server/src/hardening.rs`); an endpoint adds nothing for that. The Content-Security-Policy allows no inline script or style: in `web/`, a style that is worked out goes through a `style:` directive or a class, never a `style` attribute, and no page holds a script beyond the one in `web/src/app.html` and SvelteKit's own, which the server allows by their hash; the one style attribute allowed is the one SvelteKit gives `#svelte-announcer`, which the server reads from the build and allows by its hash too. An endpoint that makes the server reach out to an address a reader names counts it with `rate::Rates::lookup`, and whatever an account can make more of has a limit per account.
- Every type that goes out or comes in as JSON over the API derives `TS` next to `Serialize` or `Deserialize` and is listed in its module's `types`; `web/src/lib/api/types.ts` is written out of them and never edited by hand. After changing such a type, run `UPDATE_API_TYPES=1 cargo test --test api_types` in `server/` and commit the file.
- What changes for an account reaches its open tabs as an event (`server/src/events.rs`). A request through the API is announced by the layer around the API, by its address: an endpoint with a new kind of address gets a line in `events::changed` and in its test. What changes outside a request, like fetching, publishes its event itself.
- Every image that is delivered points to the image proxy: a text goes out through `images::Signer::in_html`, the address of a thumbnail, an image or an icon through `images::Signer::address`, never as it is stored. Only the proxy decodes images, within its limits for bytes and pixels.
- Only `server/src/cleaning.rs` reads HTML that somebody else wrote: its parser is kept within limits for the depth and the size of the tree, and `ammonia` with a fixed list has the last word. `clippy.toml` forbids `ammonia` and the HTML parser elsewhere. Its lists are data in `server/rules/`, not code.
- An article's number in its feed (`seq`) is given out once, without gaps, and never again. Unread counts are always worked out from the read mark and its exceptions; nothing stores a counter.
- No `unsafe`: the crate forbids it. Nothing that comes from outside (a request, a feed, a web page, an image, the old database) may bring the server down: no `unwrap`, `expect` or `panic!` on it outside tests. Errors are `anyhow` inside and `AppError` outward, which answers without giving away internals.
- New code comes with tests, and no test is switched off to get CI green. Coverage goes to Codecov and is shown on pull requests, but no percentage is required. Tests of the server run against PostgreSQL with `#[sqlx::test]`; where a simple model can serve as a comparison (what was read, the tree), test against it with random input.
- Every parser of input from outside (feeds, web pages, images, OPML, the old database, the old frontend's `localStorage`) has limits for size and count and tests with input that breaks the rules. Where our own code decides about security there is fuzzing on top, from work package 2.11 on: the cleaning, the handling of feeds and the image proxy have fuzz targets in `server/fuzz/`, the address check of the hardened HTTP client has a property test (see "Fuzzing" in `docs/architecture.md`). Their stored corpus runs as an ordinary test in CI, and whatever fuzzing finds goes into the corpus. Not every parser gets a fuzz target.
- Every text users see is in `web/src/lib/i18n/`, in English and in German; components hold no texts. The Android app's own texts are the exception, as they are not part of the page: its start page's in `app/www/texts.js`, its native ones in `app/android/app/src/main/res/values*/strings.xml`, in English and in German too. Colors come from the named variables (`bg-paper`, `text-soft`, `border-line`), so themes only recolor variables.
- To see the interface, e.g. after changing it, run `pnpm dev:demo` in `web/` for the reader with made-up data, `pnpm dev` for the one that talks to a server on `127.0.0.1:3000`, or `pnpm build:single` for the whole of it with made-up data as one HTML file.
- Components get their data from a `Reader` (`web/src/lib/reader.ts`) and nowhere else. Whatever the page can do works in both readers, the one for the server (`web/src/lib/api/`) and the one with made-up data (`web/src/lib/demo/`), or is switched off through `Reader.can` where one of them cannot do it yet.
- Tests and measurements use made-up data. No dump of the production database, no real account and no secret is ever committed; settings come from the environment, and `.env` stays out of the repository.
- Dependencies come from crates.io and the npm registry, with their lockfiles committed. Prefer crates in pure Rust, e.g. `rustls` over OpenSSL.
